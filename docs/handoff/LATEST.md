## 大判PDFの`422 PIXEL_LIMIT_EXCEEDED`: 縮小前の画素数判定を縮小後に修正（2026-10-25、PR #1171、ADR-0030追記）

### 結果
- **起点**: ヘルスレポート(2026-10-25 09:00)でkanameoneの`error`3件。`PaddleOCR request failed: 422 PIXEL_LIMIT_EXCEEDED ページ1(上限: 40000000, 実際: 41743702)`。
- **原因(実測、`measure-pdf-page-dimensions`をActionsで実行)**: 3件は同一ファイルの重複(930,297B・1ページ・1607.8×3365.3pt・200dpi換算41,743,702px)。`raster.py`の`MAX_PIXELS`検査が縮小前の200dpi換算で判定し、PR #1166の長辺上限で縮小すれば約3.0Mpxに収まるページまで拒否していた。**退行ではなく従来からの拒否**(事後確認: 直近30日の`paddle-ocr`の422はこの3件だけで、2026-10-23 15:02〜15:24 JST、リビジョン`00004-wgc`。この種の書類が初めて流入しただけ)。cocoroの`error`は0件、devの3件はseed。
- **修正**: PR #1171(`b9a80950`)。縮小して描画するPDFページは縮小後の画素数で判定。縮小しないページ・長辺上限なし・画像は不変。展開爆弾対策は、縮小後の確保量を同じ`MAX_PIXELS`で見るため維持(14400pt角でも長辺2500pxに収まるテストあり)。当初案の「ページ寸法(pt)の絶対上限を別に設ける」は、縮小後判定と重複するため採用しなかった。
- **検証**: `services/paddle-ocr/tests/` 82件PASS(CIと同じ`requirements-test.txt`)、CI全PASS、`codex review`指摘0件(1回)。dev合成PDFプローブ(1608×3365・1700×3180・A4)は全て初回200・`NO_FAILURE`・`signal 9`0件(合成PDFでの結果で、読み取り精度は未測定)。
- **反映**: dev→kanameone→cocoroに`deploy-paddle-ocr.yml`で展開(成功)。kanameoneの3件を`fix-stuck-documents --doc-id`でpendingに戻して再処理。再処理後のdry-runでkanameoneの`error`/`processing`は0件。**3件が`processed`になった個別確認は未実施**。
- **進め方の反省**: dev検証より前にPRをマージし、テスト寸法も実測前の仮定値だった。指摘を受けて以降は実測→dev検証→展開の順に是正。`paddle-ocr`の展開は手動のため、マージで本番に出ることはなかった。

### 未確認・残した点
- **縮小後の読み取り精度は、devの合成PDFで測定済み**(2026-10-25、PR #1174、ADR-0030追記)。1608×3365ptの大判ページ(縮小後の文字行の高さ約9px相当まで)で、golden4件すべてが縮小なしと同じ読み取り結果(類似度1.000)。ただし人が作った正解との一致ではなく、短いgolden・きれいな合成描画・各1回の限界がある。**実書類の読み取り結果は未測定**。
- **元PDFの埋め込み画像の実寸は未確認**。書類(個人情報を含みうる)の中身を扱う測定は、クラウド側で新規スクリプトが必要になり、見合わないため実施しなかった。縮小後の読み取り精度が問題になったときに測る(GOAL.md中断点(b)と同じtrigger)。
- **画像経路の`MAX_PIXELS`(40Mpx超の画像は縮小前の画素数で422になりうる)は未調査**。ADR-0030追記の「画像は対象外(デコードが必要)」の理由はコードで検証していない。画像で422が出たときに調べる。
- 同一ファイルが3回流入した経緯は未調査(実害なし)。
- **他の入力上限(`MAX_PAGES`・`MAX_UPLOAD_BYTES`・処理時間)は、直近30日の実データで当たっていない**(Cloud Runのリクエストログ。kanameoneは413/504が0件・422は今回の3件のみ、cocoroは0件)。全件の寸法分布の測定は行わず、アラート(`processocr_error`)の発火時に応答ステータスを見る(GOAL.md中断点(d))。
