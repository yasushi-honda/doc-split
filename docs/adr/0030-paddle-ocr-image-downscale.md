# ADR-0030: PaddleOCRの入力画像を長辺2500pxに自動縮小する(メモリは増やさない)

## Status
Accepted (2026-10-09)。ADR-0025(PaddleOCR移行)の運用上の補足。

## Context

### 発端
- kanameoneで画像書類1件が`PaddleOCR request failed: 503`で`error`になった。`paddle-ocr`のログは、毎回`Container terminated on signal 9`(強制終了)で、リトライ5回を使い切って確定していた。
- cocoroでも、修正前に同じクラッシュが1回起きていた(2026-10-09、再試行で自己回復し`error`は残らなかった)。問題は特定のクライアント固有ではない。

### 原因(devで確定)
- 合成JPEG(実データなし、`paddle-ocr-image-probe`)をdevへ送って再現した。4GiBでは、約7Mpx以下は成功、7.7〜9.2Mpxは不安定(1回目503→再試行で成功)、9.7Mpx以上(例: 4000x3000)は確実に失敗した。
- **メモリ8GiBでは、同じ画像が全て1回目で成功した。** 原因は`paddle-ocr`(4GiB)のメモリ不足と確定した(メモリ使用量そのものは未計測)。
- 当初の仮説(「長辺4000px超の縮小処理が原因」)は、4000x3000(縮小のログが出ない)でも失敗したため誤りだった。
- PDFは200dpiのA4で約3.9Mpxに収まり、これまで問題にならなかった。画像は入力寸法に制限がなく(`MAX_PIXELS`は40Mpx)、12Mpx級のスマホ写真がこの余裕を超える。Geminiは外部APIでこの制約がなかったため、PaddleOCRへの全面切替(ADR-0025)後に表面化した。

## Decision
1. `paddle-ocr`が、OCRエンジンへ渡す前に、**長辺が上限を超える画像だけ**をアスペクト比を保って縮小する(`MAX_IMAGE_LONG_SIDE`)。**既定は2500px**。縮小するのはOCR入力のみで、Storageの原本は変更しない。
2. **メモリは4GiBのまま**にする(追加費用$0)。
3. 縮小はPDFには適用しない。ピクセル数ガード(`MAX_PIXELS`、展開爆弾対策)は縮小前の画素数で判定する既存の順序を維持する。
4. 上限は環境変数で調整でき、コードの変更は要らない(`gcloud run services update --update-env-vars MAX_IMAGE_LONG_SIDE=<値>`で新しいリビジョンを作る)。ワークフロー(`deploy-paddle-ocr.yml`)には宣言がないため、**手動で設定した値はIaCに記録されない**。変更したら、`gcloud run services describe`で実値を確認し、GOAL.mdなどに必ず記録する。

### 上限を2500pxにした根拠
- 4GiBのまま、上限より大きい6種類の画像(3700x2775〜4080x3060)を順に送り、「1回目に503になった回数」を比較した(基準: 0件)。
  - 2500px: 6件すべて1回目で成功(最長86秒、`signal 9`のログ0件)。
  - 3000px: 6件中2件が1回目503、うち1件は再試行でも失敗。
- 6件の測定で、確率の見積もりとしては粗い。

### 精度確認(判定力の限界つき)
- goldenのPDF4件を3種の画像(control=200dpi、large=長辺4000px、partial=書類が画面の50%)にして、縮小あり(2500px)で期待テキストと文字単位の類似度を照合した。**12件すべて1.000**。
- ただしgoldenは大きく印字された約63〜66文字の短文で、**判定力が低い**。「縮小しても精度が落ちない」ではなく「落ちるとしてもこの確認では検出できない」。実際の小さい文字・ブレ・影・斜めの写真は再現していない。

## Consequences

**良い影響**:
- 12Mpx級の画像書類がメモリ不足で`error`になる事象が解消する(devの合成画像で確認、本番では実書類1件が再処理でリトライなしに成功)。
- 追加費用なし。処理時間も短くなる(縮小後は約3000x2250相当以下)。
- 原本は不変のため、設定変更後の再処理ができる。

**悪い影響・リスク**:
- 小さい文字の読み取り精度が、縮小で落ちる可能性がある(書類が写真の一部しか占めない撮影など)。**本番で実際の画像書類の読み取り結果を継続して確認する**。
- **大判用紙のPDF**(A3・200dpiで約7.8Mpx)は縮小の対象外で、不安定な領域に近い。実績はなく、出た時点で検討する(PDFのdpi変更はgoldenの再現性に影響するため決裁者判断)。
- 6件の測定に基づく値で、環境差(CPU・同時リクエスト・メモリの断片化)により不安定さが残る可能性がある。

## Alternatives Considered

- **メモリを8GiBにする**: dev実測では最も確実で、精度への影響もない。ただし1環境あたり月約$26(公式単価Tier 1・最小インスタンス1台の概算、実額は請求画面で確認)の増加。縮小で安定したため見送った。再発時の第一候補。
- **上限を2000pxなどさらに下げる**: 安定性は上がるが、精度への影響が大きくなる。測定していない。
- **上限3000px**: 6件中2件が1回目503で、1件は再試行でも失敗したため不採用。
- **対処しない(再試行頼み)**: 12Mpxは確実に失敗するため不採用。
