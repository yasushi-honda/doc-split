# ADR-0030: PaddleOCRの入力画像を長辺2500pxに自動縮小する(メモリは増やさない)

## Status
Accepted (2026-10-09)。ADR-0025(PaddleOCR移行)の運用上の補足。

## Context

### 発端
- kanameoneで画像書類1件が`PaddleOCR request failed: 503`で`error`になった。`paddle-ocr`のログは、毎回`Container terminated on signal 9`(強制終了)で、リトライ5回を使い切って確定していた。
- cocoroでも、修正前に同じクラッシュが1回起きていた(2026-10-09、再試行で自己回復し`error`は残らなかった)。問題は特定のクライアント固有ではない。

### 原因(devで確定)
- 合成JPEG(実データなし、`paddle-ocr-image-probe`)をdevへ送って再現した。4GiBでは、約7Mpx以下は成功、7.7〜9.2Mpxは不安定(1回目503→再試行で成功)、9.7Mpx以上(例: 4000x3000)は確実に失敗した。
- **メモリ8GiBでは、同じ画像が全て1回目で成功した。** 原因は`paddle-ocr`(4GiB)のメモリ不足と確定した(メモリ使用量そのものは未計測)。
- 当初の仮説(「長辺4000px超の縮小処理が原因」)は、4000x3000(縮小のログが出ない)でも失敗したため誤りだった。
- PDFは200dpiのA4で約3.9Mpxに収まり、これまで問題にならなかった。画像は入力寸法に制限がなく(`MAX_PIXELS`は40Mpx)、12Mpx級のスマホ写真がこの余裕を超える。Geminiは外部APIでこの制約がなかったため、PaddleOCRへの全面切替(ADR-0025)後に表面化した。

## Decision
1. `paddle-ocr`が、OCRエンジンへ渡す前に、**長辺が上限を超える画像だけ**をアスペクト比を保って縮小する(`MAX_IMAGE_LONG_SIDE`)。**既定は2500px**。縮小するのはOCR入力のみで、Storageの原本は変更しない。
2. **メモリは4GiBのまま**にする(追加費用$0)。
3. 縮小はPDFには適用しない(→2026-10-18の追記で改訂: PDFにも`MAX_PDF_LONG_SIDE`を適用する)。ピクセル数ガード(`MAX_PIXELS`、展開爆弾対策)は縮小前の画素数で判定する既存の順序を維持する。
4. 上限は環境変数で調整でき、コードの変更は要らない(`gcloud run services update --update-env-vars MAX_IMAGE_LONG_SIDE=<値>`で新しいリビジョンを作る)。ワークフロー(`deploy-paddle-ocr.yml`)には宣言がないため、**手動で設定した値はIaCに記録されない**。変更したら、`gcloud run services describe`で実値を確認し、GOAL.mdなどに必ず記録する。

### 上限を2500pxにした根拠
- 4GiBのまま、上限より大きい6種類の画像(3700x2775〜4080x3060)を順に送り、「1回目に503になった回数」を比較した(基準: 0件)。
  - 2500px: 6件すべて1回目で成功(最長86秒、`signal 9`のログ0件)。
  - 3000px: 6件中2件が1回目503、うち1件は再試行でも失敗。
- 6件の測定で、確率の見積もりとしては粗い。

### 精度確認(判定力の限界つき)
- goldenのPDF4件を3種の画像(control=200dpi、large=長辺4000px、partial=書類が画面の50%)にして、縮小あり(2500px)で期待テキストと文字単位の類似度を照合した。**12件すべて1.000**。
- ただしgoldenは大きく印字された約63〜66文字の短文で、**判定力が低い**。「縮小しても精度が落ちない」ではなく「落ちるとしてもこの確認では検出できない」。実際の小さい文字・ブレ・影・斜めの写真は再現していない。

## Consequences

**良い影響**:
- 12Mpx級の画像書類がメモリ不足で`error`になる事象が解消する(devの合成画像で確認、本番では実書類1件が再処理でリトライなしに成功)。
- 追加費用なし。処理時間も短くなる(縮小後は約3000x2250相当以下)。
- 原本は不変のため、設定変更後の再処理ができる。

**悪い影響・リスク**:
- 小さい文字の読み取り精度が、縮小で落ちる可能性がある(書類が写真の一部しか占めない撮影など)。**本番で実際の画像書類の読み取り結果を継続して確認する**。
- **大判用紙のPDF**(A3・200dpiで約7.8Mpx)は縮小の対象外で、不安定な領域に近い(→2026-10-18の追記で対象に改訂)。実績はなく、出た時点で検討する(PDFのdpi変更はgoldenの再現性に影響するため決裁者判断)。
- 6件の測定に基づく値で、環境差(CPU・同時リクエスト・メモリの断片化)により不安定さが残る可能性がある。

## Alternatives Considered

- **メモリを8GiBにする**: dev実測では最も確実で、精度への影響もない。ただし1環境あたり月約$26(公式単価Tier 1・最小インスタンス1台の概算、実額は請求画面で確認)の増加。縮小で安定したため見送った。再発時の第一候補。
- **上限を2000pxなどさらに下げる**: 安定性は上がるが、精度への影響が大きくなる。測定していない。
- **上限3000px**: 6件中2件が1回目503で、1件は再試行でも失敗したため不採用。
- **対処しない(再試行頼み)**: 12Mpxは確実に失敗するため不採用。

## 追記 (2026-10-18): 大判PDFにも長辺上限を適用する

上記のDecision 3「縮小はPDFには適用しない」と、リスク欄の「大判用紙のPDFは対象外、出た時点で検討する」を、実績が出たため改める。

- **実績**: kanameoneで2026-10-15、`paddle-ocr`が`signal 9`(503)で4回落ちた。実測(`measure-pdf-page-dimensions`)では、503が出た書類のうち2件は**1ページ目だけがA3横**(1191x842pt、200dpiで3309x2339px・約7.7Mpx)だった。
- **再現(dev、4GiB、合成PDF、実データなし、`paddle-ocr-pdf-probe`)**: A3横の1ページ目は**3回中3回**初回503になり、同時刻に`signal 9`が出た。A4(長辺2339px)と704x1000pt(長辺2778px・約5.4Mpx)は3回とも初回成功だった。
- **決定**: PDFページにも長辺の上限`MAX_PDF_LONG_SIDE`(既定**2500px**、画像と同値)を設ける。長辺が上限を超えるページだけ、**描画後に縮小するのではなく最初から縮小後の倍率で描画する**(縮小前の大きな配列を確保しない)。上限以下のページ(A4は長辺2339px)は`scale=dpi/72`のままで、**描画手順は不変**。したがって「PDFのdpi変更はgoldenの再現性に影響する」という懸念には触れない(dpiの設定値`PADDLE_PDF_RENDER_DPI`も変えない)。`MAX_PIXELS`は従来どおり縮小前の200dpi換算で判定する。
- **A3横の結果**: 長辺2500px(約151dpi相当・約4.4Mpx)。読み取り精度は未測定で、本番で大判書類の読み取り結果を継続して確認する。
- **未解明**: 本番では約5.4Mpxの書類も1件503になっているが、devの約5.4Mpxは3回とも成功した。画素数だけでは説明できず、直前の書類のコンテナ停止に巻き込まれた可能性を含めて原因は不明のまま。
- **ロールバック**: 環境変数`MAX_PDF_LONG_SIDE`に大きな値(例: `100000`)を設定する。コード変更・再ビルドは不要。
- 実装: `services/paddle-ocr/raster.py`の`pdf_pages_to_rgb`、`app.py`、診断ツール: #1163(測定)・#1165(PDFプローブ)

## 追記 (2026-10-25): PDFの`MAX_PIXELS`判定を縮小後の画素数に改める

上記(2026-10-18)の「`MAX_PIXELS`は従来どおり縮小前の200dpi換算で判定する」を、PDFについて改める。

- **実績**: kanameoneのヘルスレポート(2026-10-25)で、3件が`422 PIXEL_LIMIT_EXCEEDED`(上限40,000,000、実際41,743,702)で`error`になった。200dpi換算が上限を約4%超えた大判の1ページ目で、2026-10-18の長辺上限の縮小より**前**の検査で拒否されていた(退行ではなく従来からの拒否。縮小すれば約3.3Mpxで収まる)。
- **決定**: `pdf_max_long_side`が有効で、縮小して描画するページは、**実際に確保する縮小後の画素数**(`ceil(幅pt×倍率)×ceil(高さpt×倍率)`)で`MAX_PIXELS`を判定する。縮小しないページ(A4等)と、長辺上限を使わない場合(`None`)は従来どおりの判定で、挙動は不変。
- **展開爆弾対策が維持される理由**: 縮小するページは最初から縮小後の倍率で描画するため、縮小前の大きな配列は確保されない。確保量は縮小後の画素数で決まり、その上限を同じ`MAX_PIXELS`で見ている。PDF仕様上の最大ページ(14400pt角)でも長辺2500pxに収まる(テストあり)。
- **画像は対象外**: 画像は縮小前にデコードが必要なため、従来どおり縮小前の画素数で判定する。
- **実装・テスト**: `services/paddle-ocr/raster.py`の`pdf_pages_to_rgb`、`tests/test_raster.py`。
- **既存の`error` 3件**: コード展開後に再処理する(展開前に再処理しても同じ422になる)。

## 追記 (2026-10-25): 大判PDFの縮小後の読み取り精度の測定(dev、合成データ)

2026-10-18追記の「A3縮小後の読み取り精度は未測定」を、devで測定した(実データなし)。

- **方法**: 既存の精度確認(`paddle-ocr-downscale-accuracy`)をPDFにも使えるよう拡張した。goldenの内容(4件)を、kanameoneで422になった大判ページと同寸法(1608×3365pt、長辺2500pxへ縮小)の左上に、倍率k=1/2/2.7で配置し、A4(縮小なし)を対照にして、文字単位の類似度を取った。実行はPR #1174のブランチを指定し、マージ前に行った(Actions run 40188163163、`label=large-pdf-after-1171`)。
- **結果**: 全28件(画像12件+大判PDF12件+A4のPDF対照4件)が`status=200`・類似度1.000。縮小後の文字行の高さが最も小さい`pdf-big-k1`は、200dpiの33pxが約0.267倍になり**約9px**だった。この大きさでも、旧字体を含む4件すべてが縮小なしと同じ結果になった。
- **この測定が示すこと**: 縮小後でも、縮小なし(A4)と同じ読み取り結果になる。**人が作った正解との一致(真の精度)ではない**。goldenの正解テキストは、A4をこのエンジンで読んだ結果である。
- **限界**: ①goldenは各約62〜66文字(4行)と短く、1文字で約1.5%動く ②きれいな合成描画で、ぼけ・ノイズ・傾きがない(実書類はこれより悪い可能性がある) ③各1回の実行 ④約9pxより小さい文字(k<1)は未測定 ⑤kanameoneの実書類の文字の大きさは不明。
- **未測定のまま残すもの**: 実書類の読み取り結果(書類の中身を扱うため行わない)。問題が出たときに、その書類で確認する。
- 実装: `scripts/paddle-ocr-downscale-accuracy.ts`(`.pdf`対応)、`.github/scripts/render_golden_images.py`(大判PDFの生成)。ワークフローは変更していない(`workflow`スコープのない認証ではワークフローを変更できないため、生成スクリプト側で対応した)。
