# ADR-0026: 日付由来トークンを検索索引から外し、日付語は fileDate の範囲で答える

## Status
Accepted（PR-B: クエリ側 = 日付語の範囲検索。PR-A: 索引側 = 日付由来トークンの除外は続けて適用）

## Date
2026-09-20

## Context

`search_index/{tokenId}` は 1 トークン = 1 文書に全書類の postings を詰める設計で、Firestore の 1 文書 1MiB 上限（kanameone で約 14,500 件）に達する（Issue #984）。段階1（PR #986〜#989）で、上限に達したトークンだけをスキップし書類の全トークンを未登録にしない fail-soft と検知・復旧手段を整えたが、**飽和したトークンでは新規書類が検索に出ない**状態は残った。

kanameone の実測（2026-09-20）で、飽和・間近の上位 5 トークンはすべて日付由来だった:

- 日付トークン `YYYY`（`2026` = 14,562 件で飽和済み）
- アプリの改名規則 `書類名_事業所_YYYYMMDD_顧客名` の `YYYYMMDD` が fileName の bigram になる（`26` / `20` / `02` / `60` が 11,400〜12,780 件）

高頻度トークンは既にスコアに寄与していない（最大 df のトークンは `idf=0`、検索の第 1 ソートキーも `fileDate` 降順）。

## Decision

**日付由来のトークンを索引に持たず、日付語は `documents.fileDate` の範囲クエリで答える**（シャーディングはしない）。

- シャーディングは書込みしか救わない。`searchDocuments` は全クエリトークンの postings を展開するため、シャードが増えると 1 検索で読む文書が増え、256MiB の関数にはむしろ悪化する
- 日付は既存の複合インデックス（`status × fileDate` 昇順・降順）で範囲検索できる。新しいインデックスは不要

### クエリ側（PR-B）

- `functions/src/search/dateQuery.ts` の `extractDateFilters(rawQuery)` が、正規化**前**の生の語から日付語（年 2000〜2099・年月・年月日）を抽出し、UTC 暦日の `[start, end)` を返す。複数の日付語は共通部分
- 日付語のみ → `documents` を `where status + fileDate 範囲 + orderBy fileDate desc` で直接取得し `count()` で total。先頭 500 件のみ（OOM ガード `MAX_GETALL` と同じ `truncated` 契約）
- 混在 → 通常語で索引検索 → 候補（≤500）を `fileDate` でメモリ内フィルタ。候補の切り詰め後に絞るため、日付が候補から漏れうる（`truncated` で通知。段階3 = posting に fileDate 内包は別判断）
- 日付のみの並びは Firestore native 順（fileDate desc → docId desc）。`limit(offset+limit)` は先頭からの接頭辞が一致するため、同日内でもページ境界で重複・欠落しない（`compareSearchResults` で再ソートすると境界日の並びがページ間でずれる）

### 索引側（PR-A、続けて適用）

- `isExcludedToken(token)` を単一の述語として共有: 日付形（`YYYY` / `YYYY-MM` / `YYYY-MM-DD`、2000〜2099）と、数字・`_` だけの 1〜2 文字。`generateDocumentTokens` は date フィールドのトークンを生成しない
- 述語は tokenId ではなく**トークン文字列**で判定する（32bit の tokenId 衝突で正当なトークンを巻き込まないため）
- **述語の年の範囲と `dateQuery` の年の範囲は必ず一致させる**（不一致だと、索引から除外された年が範囲検索にも載らず 0 件になる）

## デプロイ順序（安全性を決める）

1. PR-B（範囲検索）を先に反映する。旧索引のままでも無害
2. PR-A（索引から除外）を後に反映する。PR-B が反映済みでなければ、新規書類の日付検索が索引から消えて当たらなくなる
3. `deploy-functions.yml` は全関数を一括更新するため、B と A を同じデプロイで出すと更新途中の数分間、新規書類が旧クエリで日付検索に当たらない窓が生じる（完了後は範囲検索が索引に依存しないため解消。持続的な破損ではない）
4. ロールバック: A を戻すなら B は戻さず、全件 force-reindex で日付トークンを再生成する

## Consequences

- 日付系トークンの書込みがなくなり、飽和しない。ISO 形式 `2026-09-20`（正規化でハイフンが除去され索引では当たらなかった）も範囲検索で当たる
- **挙動変更（decision-maker 許容済み）**: 数字だけの bigram・2 文字以下の数字の語が索引から消えるため、`0920` のような数字の部分一致・`20` 等の 2 桁の単独検索は縮小（2 桁は 0 件）する。1999 以前・2100 以降の年は日付として扱われない
- 日付のみ検索は先頭 500 件のみ。深い offset は約束しない
- `df` は是正しない（実件数の約 3.6 倍のまま。削除側の重複排除で負値だけ止める）
- 2b（シャーディング）は計測（非日付トークンの推定 posting 件数）を見て別途判断する
