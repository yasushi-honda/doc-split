# ADR-0031: PaddleOCRにページ向き補正を入れる(横向き・上下逆のFAX帳票が「未判定」になる事象の修正)

## Status
Accepted (2026-11-04)。ADR-0025(PaddleOCR移行)・ADR-0029(Gemini完全廃止)の運用上の修正。

## Context

### 発端
- kanameoneのかなめ様から、「今月のFAX実績処理で、先月と比べて正常に解析が完了しない帳票が多数発生している」との連絡があった(2026-11-04)。
- 添付の画面では、サービス実績記録表のFAXを2ページずつに分割した書類(`…_未判定_未判定_p1-2.pdf`等)が、書類種別「未判定」・「不明利用者」・「選択待ち」で並んでいた。プレビューは帳票が90度回転した向きで、OCR結果(1,701文字)は`2`, `1`, `1`, `4`…と数字だけだった。

### 原因(合成帳票で再現して確定)
- `services/paddle-ocr/ocr_engine.py`は`use_doc_orientation_classify=False`・`use_textline_orientation=False`で、ページの向きを補正しない。Geminiは画像を見て向きを吸収できたが、PaddleOCRは補正しないと横向き・上下逆の帳票を読めない。ADR-0025の精度評価(24文書)は向きが正常な模擬文書で、横向きは評価対象に入っていなかった。
- 架空の「サービス提供実績記録表」(A4横)を4方向(0/90度×2/180度)のPDFにし、本番と同じ設定で読ませた(ローカル、`PP-OCRv6_medium`、200dpi)。重要語13個のうち読めた数:

| 向き | 本番設定(補正なし) | 補正あり |
|---|---|---|
| 0度 | 13 | 13 |
| 90度(片方向) | 13 | 13 |
| 90度(逆方向) | **0**(出力は数字だけ) | 13 |
| 180度 | **0**(文字化け) | 13 |

- FAX品質(1728px/1200px幅・ディザ2値化・ノイズ・傾き)に劣化させた帳票でも、同じ結果(補正なし 0/13 → 補正あり 13/13、4方向×2水準)。
- 90度の片方向だけ読めるのは、PaddleOCRが縦長の切り出しを一方向にだけ回すため(推測、片方向だけ成功する事実は実測)。
- 文字が読めないと書類種別・利用者・事業所を判定できず、「未判定」「不明利用者」「選択待ち」になる。先月との差がこれで説明できるかは**未確定**。上の再現は合成帳票であり、実書類の向きは確認していない。

### 本番の件数(kanameone、2026-11-04、件数のみの集計・書類名や本文は取得していない)
`status=processed`の書類のうち書類種別が「未判定」の件数(処理日時、JST):

| 期間 | processed | 未判定 | 率 |
|---|---|---|---|
| 8月 | 5,637 | 404 | 7.2% |
| 9月 | 4,106 | 215 | 5.2% |
| 10月 | 4,258 | 338 | 7.9% |
| 11月1〜4日 | 1,735 | 144 | 8.3% |
| 8/5〜8/31(Gemini) | 4,187 | 305 | 7.3% |
| 10/5〜10/31(Paddle) | 2,795 | 283 | 10.1% |

- 「未判定」の**率は、補正の有無・GeminiからPaddleへの切替で急増していない**(5〜10%の範囲)。月別の率だけでは、先方の「先月より増えた」を横向き帳票の読み取り不能で説明できる証拠は得られていない。
- 一方、11月1〜4日の未判定は144件で、1日あたり約36件(10月は約11件)。月初に実績FAXがまとまって届くため、**件数としては月初に集中する**。先方の体感は、この月初の集中と整合する。
- 未判定の中に横向き帳票がどれだけあるかは未確認(確認には書類のPDFを読む必要があり、実PIIをローカルに置かない方針のため行っていない)。
- 集計は、2回目の追加集計(月初4日間の同条件比較・「利用者も不明」の件数)の途中で、環境の分類器に拒否され、完了していない。インデックス不足で取れなかった項目もある。

## Decision
1. PaddleOCRのページ向き分類(`PP-LCNet_x1_0_doc_ori`、約6.8MB)を有効にし、`use_doc_orientation_classify=True`にする。歪み補正・行単位の向き分類は無効のまま。
2. 向き分類モデルも、det/recと同じ方式で固定する(Hugging Faceのimmutable revision+SHA-256をビルド時に検証、起動時に再検証)。`expected-model-hashes.json`に`docOrientation`を追加し、`download_models.py`と`ocr_engine.py`が3モデルを扱う。欠けたまま起動すると横向き帳票が黙って読めなくなるため、欠落は起動失敗にする(fail-loud)。
3. det/recの重み・結合順序は変えない。

## 検証
- **回帰なし**: 正常な向きのgolden 6ページは、本番設定と補正ありでOCRテキストが完全一致(6/6、差異0)。
- **処理時間**: ローカルMacで、補正の有無とも約24〜28秒/ページ(密な表の1ページを各1回、差は測れなかった。ばらつきは未測定)。これはCloud Run実機の既存実測(p50=6.4秒、補正なし、ADR-0025 PR4c)とは別環境・別ページで、直接比べられない。補正ありの構成のCloud Run実機(dev、amd64、4GiB)は、2026-11-04に次のとおり確認した。
  - デプロイ後の`/health`は`modelLoaded:true`、`modelVersion`は変更前と同じ。golden fixture 1件のOCRテキストが期待値と一致(デプロイ検証ステップ)。
  - `paddle-ocr-pdf-probe`(合成PDF、各4ページ、1ページ目の寸法を変える。GHA run 41788794823): 3ケースとも200、`verdict=NO_FAILURE`、メモリ不足の`signal 9`のログ0件。
  - 補正を入れる前(2026-10-18、同じ3ケース)との所要時間(wallMs): 595x842は147秒→112秒、704x1000は155秒→169秒、1191x842(A3横)は187秒→147秒。**増加は見られない(ばらつきの範囲)**。ただし各1回で、GHA runner(米国)からの往復を含み、同時処理時の輻輳は測っていない。
  - 上のプローブは**向きの補正が効くことの確認ではない**(合成PDFは向きが正常)。dev実機での横向き帳票の読み取りは未確認で、kanameoneでは再処理した書類の判定結果で確かめる。
- 単体テスト(`tests/test_ocr_engine.py`、96件): コンストラクタへ補正が渡ること、3モデル各々の起動時検証(1つ壊すと失敗)、ビルド時取得が全モデルを配置すること、3者(hashes・download・runtime)のモデル種別の一致、補正角度のログ。変異検証をしたのは、補正を`False`に戻す、検証対象から1モデルを外す、角度ログを止める、の3つで、いずれもテストが失敗した。実PaddleOCRが引数名(`doc_orientation_classify_model_name/dir`)を受け付けることは、このテストでは確認できず、`inspect.signature`と合成帳票の実機再現(13/13)で確認した。

## 限界・未確認
- 合成帳票での検証であり、**kanameoneの実際の帳票は未測定**(実PIIをローカルに置かない方針のため)。デプロイ後にdevで実機を確認し、kanameoneでは「未判定」書類の再解析後の件数で確かめる。
- 向きの誤判定(正常な向きを回してしまう)は、golden 6ページ・合成帳票で0件だが、母数は小さい。罫線だけ・数字だけのページ(表の中身だけのページ)での挙動は未測定。
- すでに「未判定」で保存された書類は、この修正だけでは直らない。再解析(UIの「AIで再解析」・一括再処理)が必要。分割された子書類は親のOCR結果(`pageResults`)を継承しうるが、再解析は`pageResults`(本体・`detail/main`)をクリアするため、読み直される。
- 画面のプレビューは、元PDFの向きのまま(回転して見える)。OCRの読み取りには影響しない。
- **`modelVersion`は変えていない**(det/recのハッシュのまま)。保存される`ocrExtraction.version`で、補正前に読んだ書類と補正後に読んだ書類は区別できない。効果は「未判定」書類の再解析後の件数で測る。
- **向き分類は信頼度の閾値なしで必ず適用される**。誤判定の観測のため、回したページは警告ログ`PAGE_ORIENTATION_CORRECTED`(適用角度のみ)を出す。
- golden生成スクリプト(`scripts/generate-paddle-ocr-golden-text.py`)は意図的に補正なしのまま据え置いた(既存goldenの再現性を保つ)。補正ありとの照合は、本ADRの手順(下記)で別に行う。
- ローカルのarm64 Linuxコンテナ(Docker)は、**変更前の設定(補正なし)でもPaddlePaddleがsegfaultする**(`enable_mkldnn`の有無にかかわらず)。コンテナ内の実機確認はできず、ビルド時の取得とSHA-256検証がコンテナ内で成功したことまでを確認した。補正の実機確認は、amd64のdev Cloud Runで行う。

## 再確認の手順(向き分類モデル・PaddleOCRを更新するとき)
`scripts/verify-paddle-ocr-orientation.py`(ローカル専用、架空データ)が、下の1・2をまとめて実行する。

1. golden 6ページ(`scripts/fixtures/paddle-ocr-golden/*.pdf`)を、補正なし/補正ありの2つの構成でOCRし、テキストが完全一致すること。
2. 架空の横向き帳票(A4横の表を0度・90度×2・180度に回したPDF、必要ならFAX品質に劣化)を補正ありで読み、重要語が全方向で読めること。
3. 補正の適用角度が0/90/270/180で想定どおりに返ること(`result[0]["doc_preprocessor_res"]["angle"]`)。
