dev環境（doc-split-dev）のGoogle Drive連携先である共有ドライブは、doc-splitのdevサービスアカウント側が完全に所有・制御できるサンドボックスではなく、コンテンツ管理者権限が外部の複数アカウントに限定された実在の共有ドライブである。doc-splitの管理・運用アカウントはこの共有ドライブ内でファイル閲覧はできるが、フォルダ移動等の構造変更操作は権限不足でサーバー側に拒否される。

**Why**: Issue #871ロールアウト「段階0（devリハーサル）」の一環として、divergent状態を人為的に発生させるためPlaywright MCP経由でDrive UIからフォルダ移動を試行した。UI上は移動先選択・確定ボタンまで進めたが、実際には移動は反映されず（`classify-drive-claim-divergence`のDrive API経由の独立確認で変化なしを確認）、権限不足で静かに拒否されていたと判明。その後、外部共有ドライブへの権限付与を提案したところ、ユーザーから「共有ドライブは外部の内容。dev用アカウントの範囲外。勝手に編集してはいけない」と明確な指摘を受けた。結果的に実害（フォルダ移動の永続化）はなかったが、権限昇格の提案自体が越権だった。

**How to apply**:
- devの「Drive連携」が指すFirestore/Functions側の実装がdev環境であっても、その先に接続されている実際のGoogle Driveの共有ドライブは外部の実データである可能性を前提とする。「dev」という名称だけで書き込みテストが安全と判断しない
- Drive UIでのフォルダ移動・削除・共有設定変更などの構造変更操作をテスト目的で行う前に、対象の共有ドライブがdoc-split側で完全に所有・制御できるサンドボックスであることを確認する（望ましくは専用のテスト用共有ドライブを別途用意する）
- 確認が取れない場合は、他アカウントへの権限付与を提案する前にユーザーに承認を求める。「テストのために権限を広げる」提案自体が、外部データに対しては越権になりうる
- Google Driveの「その他の操作」ボタン等、同一形状の要素がリスト内に複数並ぶUIをPlaywright MCPで操作する際は、クリック後に対象の要素参照(ref)がリスト内の別の行にずれている場合がある。破壊的操作（ゴミ箱に移動等）の実行前には、選択状態（「n個選択中」表示・詳細パネルの対象名・`row [selected]`等）を検索して対象が意図した項目と一致することを必ず再確認してから実行する（本件で1回、隣接する実データフォルダのメニューを誤って開きかけた。実害はなかったが要注意）

**解決済み【2026-09-16】**: 根本原因はFirestore `settings/drive.rootFolderId`が外部共有ドライブの実フォルダを指す設定ミスと判明。以下の対応で解消した:
1. dev専用の新規共有ドライブ（Google Workspaceアカウントで作成、個人Gmailアカウントでは共有ドライブを新規作成できない）を用意し、アプリ自身の設定画面（Google Picker経由の正規UI、Firestore直接編集ではない）で`rootFolderId`を切り替え
2. 混入していた既存の合成テストデータ（1階層のフォルダツリー、配下は全て`scripts/seed-dev-data.ts`由来と確認済み）をゴミ箱へ移動（30日間復元可能、外部の実データへの影響なしを3系統で独立確認）
