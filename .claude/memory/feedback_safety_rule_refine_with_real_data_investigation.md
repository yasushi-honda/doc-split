承認制の破壊的ツールで、レビューの指摘を「念のため一律拒否」として入れた安全規則は、本番の実データで初めて過剰と分かることがある。規則を緩めるときは、推測ではなく**阻害された実体のread-only調査**を先に行い、本当に危険な条件(何が壊れるか)に絞る。

**Why**: 再帰統合ツールの計画に「ショートカットは一律拒否」を入れたところ、kanameoneのplanで1件が阻害になった。read-only調査(`inspect-drive-items`)で、移動されるサブツリー内の自己参照型で、参照先もサブツリーごと移るだけで統合後も有効と判明。本当に危険なのは「参照先が空にしてtrashされるフォルダ」(リンク切れ)だけだった。規則を「参照先がtrashされるフォルダ/参照先不明」に絞り、plan取り直しで阻害0件になった。緩和後もcodex reviewは統合先側の未走査の穴を見つけた(緩める側はレビューで抜けが出やすい)。

**How to apply**:
- 阻害が出たら、緩める前に実体を調べる(出力はPII対策でIDと種別のみ)。調査手段が無ければread-onlyの調査スクリプトを作る
- 緩和後の規則は「何が壊れる条件か」を明示して実装し、許容する側にも拒否する側にもテストを書く
- 緩和はdecision-makerの判断(安全規則の変更)として、調査結果と選択肢を示してから行う
- 検知できない限界(今回は統合対象外のショートカット)はrunbookとplan出力に明記する
